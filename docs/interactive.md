# Interactive sessions

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

**Runner-only status:** the legacy Tailscale-header listener is refused.
The opt-in [gateway listener](#gateway-deployment) authenticates network
clients with a per-run secret. It does not isolate the listener from the
agent running as the same user. Do not create a second user or enable a
local credential holder.
[#536](https://github.com/cgwalters-forge/agentic-job/issues/536) remains the
owner of session work; the [inventory](plan.md#runner-only-hardening-inventory-2026-11-05)
records the migration and missing evidence. Apart from the gateway deployment
below, this page describes the legacy design.

## Gateway deployment

Threat: a client that can reach a job pod can forge Tailscale identity headers
and attach ahead of the operator. For jobs without an overlay-network identity,
an operator-only gateway can instead reach an explicitly configured ACP listener:

```toml
[session]
listen = true
bind-address = "0.0.0.0:7790"
idle-minutes = 10
```

`bind-address` is an IP literal and nonzero port (IPv6 uses `[::]:7790`).
Without `listen = true` it is inert. Without `bind-address`, the old loopback
Tailscale mode remains refused on runner-only jobs. Direct mode does not start
`tailscale serve` or require its endpoint file. `operators` and `capability`
must be empty: identity headers grant no access in this mode.

The runner generates a fresh 32-byte random value for **each run**, encodes it
as 64 hexadecimal characters, and supplies it as `AGENTIC_JOB_ATTACH_SECRET`
to `agentic-job run`. It also delivers that value privately to the gateway,
bound to the run's endpoint. Never put it in TOML, an endpoint URL, a job
summary, a dispatch comment or a committed pod manifest. Missing, empty or
malformed secrets stop the run before the agent starts. The value is excluded
from the agent's inherited environment and registered with output redaction.

On every backend WebSocket upgrade the gateway sends exactly one header:
`Authorization: Bearer <64-hex-character secret>`. Missing, wrong or duplicate
authorization is refused with HTTP 403, leaving the attach slot available.
The gateway should omit `Origin`; if it sends one, it must occur exactly once
and match an entry in `session.origins` (at most 16). A correct secret never
bypasses this browser-origin check. ACP messages and the single-client session
lifetime are unchanged. A second client is closed; it cannot take over a run.

The gateway authenticates the operator on its frontend, keeps the backend
secret server-side, and strips any browser-supplied backend authorization.
Use TLS for the frontend and an encrypted/trusted backend network: the listener
itself speaks plain WebSocket, not TLS. Restrict pod ingress to the gateway
(for example with a Kubernetes NetworkPolicy); do not publish this port through
a public Service or Ingress. Remove the gateway's run mapping and secret when
the run ends. The reusable Actions workflow does not supply this mode or its
secret; the self-hosted runner must inject them.

This secret authenticates **remote clients**, not the agent: the agent shares
`run`'s uid and can inspect its environment or memory. The job pod is the trust
unit, not a boundary between agent and listener. Do not treat this mechanism
as an independent operator identity or approval for a write. Attach only adds
prompts/cancellation; output bounds and policy remain fixed and all forge
writes still go through end-of-run check and apply, never through the gateway.

## Legacy design

Partly built in the legacy implementation: a session run ([session runs](../specs/session.md))
accepts an operator's prompts after its task's turn, through a bridge
that listens on the runner's tailnet name behind `tailscale serve`. What follows is the earlier design note: a person, or another
program, attaches to the agent's session and works with it, while the
agent stays inside the same [sandbox](sandbox.md),
[inference proxy](inference.md) and [safe-outputs](safe-outputs.md)
limits as an unattended run. It is why the agent is driven over ACP.

The operator's words: "Another use case I have btw is interactive
chats this is why ACP. We just mix in Tailscale or equiv. Should be a
clean mode flag to wait for a connection. Or start from a prompt but
accept dynamic connections."

The [plan](plan.md#interactive-sessions) defers this work. The proposed
first bridge is a Unix socket on the
runner, reached by an `attach` command over Tailscale SSH that copies
its standard input and output to the socket: ACP stays a byte stream,
nothing new listens on the network, and the tailnet's own identity
decides who gets in. Everything below is a proposal.

## What exists

One seam, in `session/clients.rs`. The [session](harness.md) holds
ACP's `Client` role toward the agent. Every message from the agent
passes through one tap, which records it and hands the agent's notifications
to a list of attached clients. The list is empty for a task run; in a
session run it holds the bridge's one client, which
[the spec](../specs/session.md) describes with its trust boundaries.

The ACP SDK's `Proxy` role is not what this builds on. It speaks
`_proxy/*` to a conductor that owns both of its connections, and a run
with no client side has nothing for a conductor to own.

## Still to design

[The session spec](../specs/session.md) settles the way from a client
to the agent (prompts and cancels over the bridge), who answers a
permission request when a person is watching (the run's policy, still),
how a prompt sent during a turn is held (it is refused: Claude Code's
adapter would end the running turn for it) and what ends a session with
a client (the client leaving, or an idle timeout). Still open is a
client that joins a session already running: the bridge's client is
attached when the session starts.

## Who may attach

A client is a new source of instructions with the authority of whoever
is typing, but it cannot widen the run: the safe-output types, the
target, the egress policy and the limits are fixed before the agent
starts, and nothing sent over ACP changes them.

This assumes `run` without `--runner-home`, where the agent is a second
user (the reusable workflow's `agent-user: sandbox`). By default the
reusable workflow, and `review.yml`, pass `--runner-home`, which
makes the agent the runner's user and refuses `session.listen`, since
the agent could reach the bridge's port ahead of the operator, so no
client can attach there.

The user a client logs in as must not be the runner's user. That user
holds the job's credentials even after setup removes its root access.
SSH as that user would admit a credentialed user, not a chat client.
Attaching needs a user of
its own that can open the socket and nothing else. The tailnet's rules
must also keep one runner from logging in to another.

Also open: several clients at once, a read-only client, and a
WebSocket bridge for a browser client, which would have to
authenticate the client itself.
