# Testing Farm as an external execution host

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

This is a design draft for
[#3406](https://github.com/cgwalters-forge/agentic-job/issues/3406):
GitLab CI as the trusted caller, Testing Farm VMs as the execution host.
It is grounded in a working deployment of exactly that shape — a loop
that has shipped real agent runs on real RHEL guests since November 2026,
described below without links, since the instance is internal. The goal
is that this loop becomes **just configuration** for agentic-job, the
same way the in-runner review flow already is.

## The problem, and what a deployment already answers

The issue asks for two things that today's tree does not have:

1. A trusted caller that is a GitLab CI pipeline rather than a GitHub
   Actions workflow. The check and apply binaries are host-agnostic, but
   the run/artifact correlation in `external.rs` speaks only the Actions
   API: the caller record is `GITHUB_REPOSITORY` / `GITHUB_RUN_ID` /
   `GITHUB_RUN_ATTEMPT`, the matched run is found through
   `workflow_dispatch` runs, and the artifacts are Actions artifacts with
   API digests.
2. An execution host that is an ephemeral VM provisioned on demand,
   rather than a GitHub-hosted or self-hosted Actions runner.
   `docs/dispatch.md`'s external VM runner model currently means an
   external GitHub repository with self-hosted Actions runners.

A deployment that answers both end to end has been running since
November 2026 on an internal GitLab instance with Testing Farm guests
(three-plus real dispatched runs shipped, including two safe-outputs
proposal runs that produced open draft merge requests). Its shape:

- A manual GitLab CI job submits a Testing Farm request via a ~200-line
  Python script: fmf URL/ref/plan, one environment (compose, arch), and
  the TF API key from a private secrets repository reached with a
  read-only deploy token.
- Testing Farm provisions a RHEL 9.10 VM; tmt runs an fmf test that
  launches an opencode agent from a SHA-pinned container image
  (`tests/scripts/run-agent.sh` in that deployment, a ~40-line script).
- The agent does one bounded unit of work, reading state from a GitLab
  tracker item with a read-only token and writing exactly one state note
  proposal, or a patch plus one-line JSONL for safe-outputs runs, into
  `TMT_TEST_DATA`.
- A privileged CI job downloads the test-data artifacts from the Testing
  Farm artifacts server, re-validates the proposal (draft title, footer,
  no quick actions, clean `git am`) and publishes to the forge. The
  guest never holds a forge write credential.

What that deployment proves is the **contract**, not the tooling: the
tooling it uses is a reimplementation of the safe-outputs discipline
precisely because the GitLab publisher and the caller correlation did
not exist when it was written. Both now do, or are specified (#3604 for
the GitLab publisher, #3605 for the caller record spec). The rest of
this document describes the contract the deployment validated, mapped
onto agentic-job's existing vocabulary, and what would have to change
to absorb it.

## Actors and the trust boundary

There are three parties, and the design lives or dies on which of them
holds what:

- **The caller** — a GitLab CI pipeline in the repository that owns the
  dispatch configuration. It holds the Testing Farm API key, the
  read-only state token, and (in a separate privileged job) the forge
  write token. It is the only party trusted to correlate a run with its
  policy and its artifacts.
- **The host** — Testing Farm. It provisions a single-use VM, runs the
  requested test in it, and stores the test's data directory as
  downloadable artifacts. It is trusted for provisioning and artifact
  storage, nothing else: it does not vouch for the agent's output, and
  the caller verifies everything it fetches.
- **The job** — the agent, in a container inside the guest, run as an
  unprivileged user by the test harness. It holds no model key of its
  own beyond a scoped, short-lived inference credential (see below), a
  read-only tracker token, and nothing that can write to any forge.

This is the same three-party split as the GitHub Actions deployment:
caller = the reusable workflow's caller, host = the Actions runner,
job = the sandboxed agent step. The only structural difference is that
the "runner" is now behind a provisioning API, and the artifacts channel
is the host's artifact store rather than the forge's.

## The host contract

A Testing Farm host, or any ephemeral-VM host, fits the existing model
as a **provisioner** behind a small interface. What the deployment
exercised, restated as a contract:

**Request submission.** The caller POSTs a request naming a test
definition (fmf URL, ref, plan name) and one environment (compose,
arch). The request carries the TF API key and a set of request
"secrets" (below). The response's request ID is the host-side identity
of the run. The caller writes that ID to a file **before** doing
anything else with it: the request ID plus the caller's own pipeline
identity is the correlation record. This is the direct analogue of the
Actions `Record` in `external.rs`, with the GHA-specific fields
(`workflow`, `referenced_workflows`, Actions artifact IDs) replaced by
caller-owned GitLab identity and host-owned artifact identity.

**Guest lifecycle.** The host boots the VM, runs the test as its own
harness user (tmt runs tests as root on the guest in the deployment;
the agent container inside drops to an unprivileged UID), and destroys
the VM with the run. The caller polls the request until a terminal
state (complete / error / cancelled) under a hard deadline, and treats
a timeout as a failure to fetch, never as success. Single-use
ephemerality is a property the caller relies on: a leaked in-guest
credential dies with the VM, so the credential architecture below is
designed for "revocable and short-lived" rather than "never crosses the
wire" — though the wire is TLS to a trusted host either way.

**Egress channel.** The agent's deliverables — the state note or the
patch plus one-line JSONL proposal — are plain files in the test's data
directory (`TMT_TEST_DATA`), which the host publishes as downloadable
artifacts. The privileged applier job fetches them over TLS with the
host's artifact credentials, then validates everything: bounded size,
flat regular files, exact expected names, patch applies cleanly. The
channel carries data, not authority: nothing in the artifact is
executed, and no credential ever rides in it. This is the
[other CI systems](safe-outputs.md#other-ci-systems-and-deterministic-proof)
consumption model with the artifact hop made concrete.

**Where the boundary sits.** The agent job ends when its proposal files
land in the data directory. Check runs in an unprivileged caller job
against caller-owned context; apply runs in a privileged caller job
with the forge write token obtained only there. Neither check nor
apply, nor any credential they hold, ever touches the guest. The
deployment validated the discipline in this exact placement and found
no need to relax it.

## Credential architecture

Four credentials, each with one place it may exist:

1. **The host API key** (Testing Farm). Only in the caller. In the
   deployment the CI job holds a read-only deploy token to a private
   secrets repository and pulls the TF key from it at runtime, so the
   key value is not a CI variable at all; that indirection is a caller
   convenience, not part of the contract. What the contract needs is:
   the key never reaches the guest, and the caller never accepts a
   host-side claim of success that it did not fetch and verify itself.
2. **Request secrets.** Values the caller wants present in the guest
   environment, sent in the request's `secrets` (not `variables`)
   section, so the host censors them in all artifacts and logs. In the
   deployment these are the bootstrap pair for the secrets repository
   (read-only deploy token + URL) and the read-only tracker token.
   Censoring matters: a value forwarded as a plain environment variable
   appears verbatim in the host's logs of the guest environment.
3. **In-guest read-only state access.** A `read_api`-scoped project
   access token for the tracker, forwarded as a request secret. The
   agent uses it to read the item it was dispatched for and prior state
   notes — the multi-run state accumulation pattern — and nothing else.
   A read-only leak is a bounded, revocable harm.
4. **The forge write token.** Only in the privileged applier job, in
   the caller's CI secret facility, exposed as `SAFE_OUTPUTS_TOKEN`
   per the existing CLI contract. This is the only write credential in
   the entire loop, and the guest is structurally incapable of
   reaching it.

**Inference** needs its own paragraph, because it is the one place the
deployment knowingly differs from `run --runner-home`'s current rule.
The rule refuses raw API keys on the runner, for a threat model of
same-UID credential theft on a shared, long-lived machine. A
single-use guest that is destroyed with the run changes the second
half of that threat model but not the first: an agent process can
still exfiltrate a key it holds while it runs. The deployment's
answer is a **scoped inference key fetched at runtime from a
read-only secrets repository by the guest itself**, so the key is (a)
not a CI variable, (b) not in the request payload beyond the bootstrap
token that fetches it, and (c) revocable and cheap to rotate
independently of the loop. Whether that justifies a documented
`ephemeral-host` inference profile in `run`, or whether the broker
model should be extended to serve guests, is an open question below —
deliberately not decided here, because it is an operator threat-model
decision, as the #3406 findings already concluded.

## Image pinning

The deployment runs one agent container image, published as
`registry.example/agent:<full commit SHA>`, consumed identically by two
flows: the in-runner MR review flow (a CI job pulls the image by SHA)
and the TF guest flow (the guest's test script pulls the same image by
the same SHA and runs the agent in it, with the test data directory
bind-mounted at the same path so proposals land in the artifacts).
One SHA, both worlds, no moving refs.

For agentic-job the mapping is: the pinned-source discipline that
already governs the binaries and workflow files extends to the agent
image. A host profile names the image by digest or full commit SHA;
the guest script does a pull-by-digest and refuses anything else. The
image being the same across flows is what makes a TF-guest run and an
in-runner run comparable evidence — same agent, same model wiring,
only the execution host differs.

## What would change in agentic-job

Concrete, smallest-first:

1. **A caller-agnostic correlation record** (design already split out
   as #3605). `external.rs`'s `Record` and `caller_policy` are
   parameterized on caller identity: today's
   `GITHUB_REPOSITORY/RUN_ID/RUN_ATTEMPT` becomes a caller kind plus
   its identity tuple (`CI_PROJECT_PATH`, `CI_PIPELINE_ID`,
   `CI_JOB_ID` and attempt analogue for GitLab), with the same
   construction rules — written by the caller before dispatch, never
   downloaded from the run, validated before any artifact is trusted.
   The artifacts fetch similarly grows a caller-kind branch: GitLab
   job artifacts (by job ID and artifact name, digest-verified) in
   place of Actions artifacts. The Actions path stays the default;
   nothing about it changes.
2. **A provisioner surface for external VM hosts.** Not a trait with
   many implementations to start: one module, `provision`, with
   Testing Farm as the reference implementation, exposing submit /
   poll-to-terminal / fetch-artifacts / cancel, used by the dispatch
   caller the way the deployment's Python script uses the TF REST API
   directly. Artemis and others can arrive later behind the same four
   operations. This lives in `crates/agentic-job` beside `external`;
   the workflow crate stays unaware of it.
3. **A host profile in the dispatch configuration** — a section
   naming the provisioner, the compose, the test entry (fmf plan), the
   agent image by digest, and the request-secret names to forward
   (names, never values; values come from the caller's CI variables at
   runtime). The caller repository then holds only config plus the
   pinned binaries, which is the configuration-only goal of #3406.
4. **The inference decision** above, if maintainers want a native
   ephemeral-host key mode rather than leaving it to the caller's
   harness, as the deployment does today.

What the deployment already does that needs **no** change: the
safe-outputs JSONL vocabulary and check/apply discipline (the
deployment's `apply_safe_outputs.py` is a strict subset of
`apply --forge gitlab`'s checks — draft title, footer, no quick
actions, clean `git am`, one MR per run); the per-forge bounds
sections; the GitLab publisher itself.

## What stays outside

tmt, fmf and composes are Red Hat's test tooling, not agentic-job's.
The provisioner contract above deliberately speaks only of "a test
entry the host knows how to run" and "a data directory the host
publishes"; the fmf URL/ref/plan triple is one encoding of that, and
the reference implementation should keep it in configuration rather
than in code. Host-side CA chains (an internal artifacts server with a
corporate root) similarly stay the caller's problem — the deployment
carries the CA file next to its applier script, and that is the right
place for it.

The guest-side harness details also stay outside: how the guest pulls
and runs the agent image, how it bind-mounts the data directory, and
the root-harness-facts / unprivileged-agent split the deployment uses
for validation work (the guest's test harness, running as root, may
gather host facts the container agent then reasons about — a useful
pattern, but a caller concern, not a contract).

## Open questions

- **Inference on ephemeral guests.** Is a documented
  `ephemeral-host` api-key/token-file mode in `run` acceptable with
  its bound stated, or must the credential broker be the only path?
  The deployment's runtime-fetched scoped key is a middle position:
  no CI variable, no broker, single-use guest. This is the one item
  the #3406 findings explicitly left as an operator threat-model
  decision.
- **Correlation strength without Actions digests.** GitLab's job
  artifact API does not hand back a server-computed digest the way
  Actions artifacts do. Is a caller-computed digest over the fetched
  bytes (recorded in the caller record before dispatch of the applier)
  an adequate replacement, or should the record carry the artifact's
  identity some other way?
- **Host artifact trust.** The caller fetches artifacts from the
  host's artifact server with host credentials. Is the host trusted
  for artifact integrity (TLS + a trusted internal CA) sufficient, or
  should the guest also write a digest of its proposals somewhere the
  caller can cross-check? The deployment relies on the former.
- **Cancellation and cost bounds.** A hung guest burns a VM for the
  poll deadline. Should the provisioner surface expose cancel-on-
  deadline as a first-class operation (the deployment just abandons
  the request and lets the host's own timeout reclaim it)?
- **Where the state-note pattern lands.** The deployment's
  one-state-note-per-run back to a tracker item is a narrower output
  than the safe-outputs vocabulary (a comment with no write target
  beyond the item). Should that be a checked output type of its own,
  or is an `add_comment` proposal checked and applied like any other?
